# FINDINGS — bugs / misleading data

The recurring theme: **signals recorded live carry absolute epoch
nanosecond timestamps, but every number the user can see is in seconds
relative to the recording start.** Three features compare one against the
other.

## B1 — HIGH: "Save chart… custom time range" exports nothing for recordings
`SignalIO.cpp:521` compares `fromSec/toSec × 1e9` against **absolute**
timestamps. The dialog is pre-filled from the chart's X axis, which is
**relative** seconds. For recorder data every reachable range matches no
samples → "Nothing matched filters" (or silently truncated data for
partially-overlapping values). Works only for 0-based imports — the
inconsistency itself is the trap.
*Pinned by:* `CsvWriter.DISABLED_SaveChartCustomRangeMatchesChartRelativeSeconds`.

## B2 — HIGH: Slice / BandZero / BandKeep use absolute seconds on time signals
`Slice(A, 0.2, 0.5)` keeps samples whose **absolute** timestamp ∈
[0.2 s, 0.5 s] of the Unix epoch — for a recording that is *no samples*;
`BandKeep` zeroes the entire signal. The user reads 0.2–0.5 s off the
chart, gets an empty/zeroed result, and may conclude the data contained
nothing there. (`FunctionRegistry.cpp` `impl_Slice` / `bandMask`.)
Frequency-domain use is unaffected (bin 0 sits at 0).
*Pinned by:* `FunctionCorrectnessKnownIssue.DISABLED_SliceSecondsAreRelativeToSignalStart`,
`…DISABLED_BandKeepTimeWindowRelativeToSignalStart`.

## B3 — MEDIUM: revertFFT loses the start time
`revertFFT` rebuilds the waveform starting at t = 0 instead of the source
signal's first timestamp (`FunctionRegistry.cpp` `impl_revertFFT` —
the spectrum simply doesn't carry t₀). Overlaying the reconstruction with
a recorded original puts them ~55 years apart on the shared axis; the
Time view then spans 1.7e9 s and both traces look "gone".
*Pinned by:* `FunctionCorrectnessKnownIssue.DISABLED_RevertFftPreservesStartTime`.

## B4 — MEDIUM: XY view fabricates points outside the Y signal's range
`AnalyserPlot.cpp` local `interpAt`'s own comment promises NaN outside
Y's range ("the curve simply skips that X sample rather than
extrapolating") — but the code clamps to Y's first/last value, drawing a
flat fabricated line where no Y data exists. An engineer reading the XY
curve cannot tell real data from the clamp artefact.
*Pinned by:* `AnalyserPlotLayoutTest.DISABLED_XyOutsideYRangeLeavesGapNotFabricatedPoints`.

## B5 — DECISION NEEDED: division by zero silently yields 0
`FormulaEngine.cpp` (`/` operator) and `Mod(x, 0)` return **0** where the
mathematical result is ±∞/undefined. 0 is a plausible-looking fabricated
value (e.g. an efficiency = P_out/P_in formula reads "0 %" exactly where
the input dropped out, not "no data").
*Documented by:* `FunctionCorrectness.DivisionByZeroCurrentlyYieldsZero_Characterization`
(an enabled characterization test pinning the status quo so any change is
deliberate).

## B6 — LOW: same-grid fast path can silently mis-pair samples
Binary ops treat two signals as "same grid" when count + first + last
timestamps match (`FormulaEngine.cpp` path 2, mirrored in
`FunctionRegistry.cpp`), pairing by index. Two non-uniform grids that
happen to share endpoints and count get combined sample-by-sample at the
wrong times, with no warning. Unlikely but silent.

## B7 — LOW: crosshair readout shows the next sample to the right
`ScopePlot::updateCrosshair` uses `findBegin(xCoord)` → the value of the
first sample **at or after** the cursor, not the nearest one. On sparse
signals the read-out can show a value up to one full sample early.

## B8 — FOOTNOTE: non-ns-representable rates shift the FFT axis by ~5e-10
Rates like 1024 Hz (period 976562.5 ns) can't be stored exactly in
integer-ns timestamps; FFT re-derives fs from the rounded grid (relative
error ~5e-10 — physically negligible). Bin timestamps also use a
truncating cast (≤1 ns). Worth a tidy-up (`llround`), not a correctness
problem at engineering scales.

## B9 — COSMETIC: H5 import table labels a spectrum's span as seconds
The converter's HDF5 channel selector computes "Duration" from
timestamps; for a saved frequency-domain channel that is the Hz span
displayed as "… s".
